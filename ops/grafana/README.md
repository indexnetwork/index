# Grafana for Index

Provisioning files for the Grafana service on Railway (project Index, environment main). Grafana 13.x, file provisioning, no plugins.

## Datasources

| Name | uid | Role | Data |
| --- | --- | --- | --- |
| Index | `index-pg` | `grafana_ro` | the `analytics` views on the production database |
| Index Trace | `index-trace` | `grafana_trace_ro` | the `trace` schema on a Neon dev branch (`trace-proto`) |

`grafana_trace_ro` is read-only and has no access to `public` or `analytics`. Its password is read from `TRACE_PG_PASSWORD`; the Index password from `INDEX_PG_PASSWORD`. Neither is in this repository.

## Dashboards

- Folder Index: `dashboards/*.json` (activation, negotiation, opportunity, retention, supply, email), generated by `gen-index-dashboards.py`.
- Folder Index Trace: overview, drill-down (variable `interaction`) and adversarial boards, generated by `gen-trace-dashboards.ts` (`bun ops/grafana/gen-trace-dashboards.ts <outdir>`).

The Index Trace boards show real negotiation text from a pseudonymized dev branch. They sit behind the Grafana login; anonymous access is off.

## Email board

`dashboards/email.json` (Index - Email) shows daily sent, opened and clicked counts, open and click rates, delivery problems, and a table by email type. It reads `analytics.email_events`, a view over `public.email_events`, which the API fills from Resend webhooks (`services/api/src/controllers/resend-webhook.controller.ts`). Nothing appears until all of these are done, in this order:

1. Deploy the API with the `0015_email_events` migration applied.
2. Run `sql/email_analytics.sql` once as the database owner to create the view and grant it to `grafana_ro`.
3. In Resend, add a webhook to `<API_URL>/api/webhooks/resend` with the email events (sent, delivered, delivery delayed, bounced, complained, failed, opened, clicked), and set its signing secret as `RESEND_WEBHOOK_SECRET` on the API service. Without it the endpoint answers 503.
4. In Resend, open tracking and click tracking must be on for the sending domain (`agent.index.network`). They are on: the tracking `CNAME` `links.agent` is verified, and sending is verified (DKIM and SPF). Without them there are no opened or clicked events. Tracking is per domain, so Resend also rewrites the links in untracked email such as magic links; their events are ignored here.
   - The domain page shows "partially verified" only because the optional receiving `MX` (`agent`) is pending and the optional `_dmarc` record is not set. Neither affects sending or these counts. Index does not receive mail through Resend; the `_dmarc` record (`v=DMARC1; p=none;`) is worth adding in Cloudflare.
5. Rebuild and redeploy the bundle (below) so the board is provisioned.

Each tracked send is tagged with the recipient's user id, so the board also counts users (emailed, opened, clicked), and two panels join email to the rest of the analytics: users who were active within 24 hours of a click (Index - Email), and weekly active users who clicked an email that week (Index - Retention). Those joins show association, not cause. The boards show counts only, never user ids, but `analytics.email_events` carries `user_id` and anyone who can query the Index datasource can read it, so keep that datasource to people who may see per-user email behaviour.

Counts start from the day the webhook is on. Resend does not replay earlier events. Opens are inflated by Apple Mail Privacy Protection and by security scanners that open links, so read the open rate as an upper bound and trust clicks more.

## Delivering the files to Railway

The service runs the stock Grafana image. The provisioning files are packed into a tar.gz, base64-encoded and split into 500 character chunks, because the variable API rejects long values.

```bash
ops/grafana/build-bundle.sh /tmp/gb
```

The script writes `bundle.tgz`, `bundle.b64` and `chunks/TR_00..TR_NN`, and prints the start command. The tar is deterministic, so the same sources give the same sha256.

1. Set each chunk as a service variable (`TR_00`, `TR_01`, ...) and `TRACE_PG_PASSWORD`.
2. Set the printed start command.
3. Redeploy.

The start command reassembles the chunks, checks the sha256, and extracts into `/`. If the check fails it prints `bundle-check-failed-using-previous` and unpacks the earlier Index-only bundle held in `IDX_00..IDX_10`, so a mistyped chunk cannot leave the service without dashboards. It always ends with `exec /run.sh`. Once the new bundle has run cleanly for a while, the `IDX_` variables and the fallback can be removed.

A healthy deploy logs `/tmp/b.tgz: OK` and then `finished to provision dashboards`.

## Notes

- Dashboards are written under `/var/lib/grafana-dashboards` and `/var/lib/grafana-dashboards-trace`; the dashboard providers in `provisioning/dashboards/index.yaml` point at them.
- `IDX_TEST` and `GF_DATABASE_WAL` are stray variables from earlier setup work on the service. They are harmless and were left alone.
