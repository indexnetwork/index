## 🟡 Important

### I1 🟡 Questions bypass the digest's delivery/idempotency bookkeeping

**Where**
`skills/index-network/scripts/build-daily-brief-context.ts:792`, `stage-daily-brief.ts:179`, `send-daily-brief.ts:145-153`, `skills/edge-esmeralda/prompts/send.md:27`

**Code**
```ts
const questionResult = await fetchPendingQuestionsFromMcp({ apiKey, mcpUrl });
// ...
lines.push(`**One for you:** ${pendingQuestions[0].prompt}`);
```

**Why**
Opportunities have a full delivery loop: `readDeliveredIds`/`filterDedupedOpportunities` dedupe against `memory/heartbeat-state.json`, `digest-opportunity` markers carry ids through the body, and the send pass calls `confirm_opportunity_delivery` for each (`send-daily-brief.ts:145` — `const opportunityIds = extractDigestOpportunityIds(body);`). Questions capture `id`/`mode` into `BriefQuestion` but never use them: no marker, no state entry, no delivery confirmation back to Index. A question that stays pending (user doesn't reply) is re-staged verbatim every single day, and Index never learns it was delivered.

**Fix**
Mirror the opportunity pattern: embed a `digest-question:id=…` marker, record delivered question ids in heartbeat state (or skip re-delivery within N days), and/or confirm delivery via MCP in the send pass.

**Alt**
If daily repetition-until-answered is intended product behavior, document it in prepare.md/send.md and add a test pinning it.

### I2 🟡 "One for you" bypasses `hasVerifiedContent` gate and renders after the sign-off

**Where**
`skills/index-network/scripts/stage-daily-brief.ts:172-181`, `skills/edge-esmeralda/prompts/prepare.md:39`

**Code**
```ts
lines.push("That's it for now. You can always ask me for more detail, or any other questions you have!");

const pendingQuestions = context.questions ?? [];
if (pendingQuestions.length > 0) {
```

**Why**
The pointer-only fallback fires when `!hasVerifiedContent` (`stage-daily-brief.ts:168-170`), and prepare.md:39 promises "the pointer-only fallback if there is nothing else" — but the question block is appended unconditionally after the closing line, so a nothing-verified digest still carries a question, and every digest ends with content *after* the terminal-sounding "That's it for now…" line. The `---` separator suggests a deliberate P.S., but the contract docs don't sanction it.

**Fix**
Either gate the question section on `hasVerifiedContent` (or fold it before the closing line), or update prepare.md/send.md to document the postscript placement and its presence in fallback digests.

### Q2 🟡 `parsed.success` declared but never checked `[precedent-weighted]`

**Where**
`skills/index-network/scripts/build-daily-brief-context.ts:728-729`

**Code**
```ts
const parsed = JSON.parse(text) as { success?: boolean; data?: { questions?: unknown[] } };
if (!parsed.data?.questions || !Array.isArray(parsed.data.questions)) return { questions: [], source: "mcp" };
```

**Why**
A `{ success: false, error: … }` payload (no `data.questions`) falls through the guard and returns `{ questions: [], source: "mcp" }` — a *successful empty fetch* — so `questionSource` stays `"mcp"` and no warning is pushed, masking the failure. Precedent: MCP response-shape handling on this file required three 30-day follow-up fixes (`064b44e`, `9c183f6`, `d3b831c`).

**Fix**
Return `{ questions: [], source: "unavailable" }` when `parsed.success === false` (and push a warning), reserving `source: "mcp"` for genuinely successful responses.

## 🔵 Suggestions

### Q1 🔵 Error detail discarded on all three failure paths

**Where**
`skills/index-network/scripts/build-daily-brief-context.ts:714, 722, 740-741, 796`

**Fix**
The opportunities path warns with detail (`opportunities MCP unavailable: ${err.message}`, :777) while questions emit a bare `"questions MCP unavailable"` (:796) after `initResp.error` (:714), `toolResp.error` (:722), and the bare `catch` (:740) each discard the message. Thread the failure reason into the returned `{ source: "unavailable", reason? }` so the diagnostic warning carries it.

### S1 🔵 MCP-sourced `prompt` interpolated raw into the delivered digest *(weakened from 🟡)*

**Where**
`skills/index-network/scripts/stage-daily-brief.ts:179`

**Fix**
The composed body does pass through `sanitizeDigestUrls` at stage (:260) and send (`send-daily-brief.ts:159`), and opportunity prose is interpolated with equivalent rawness (stage-daily-brief.ts:81-142), so this extends an existing trust posture rather than opening a new sink — but URL sanitization does not cover markdown/structural injection (e.g. a prompt containing `digest-opportunity` markers or section headers). Consider length-capping and stripping markdown control sequences from `prompt` before interpolation.
