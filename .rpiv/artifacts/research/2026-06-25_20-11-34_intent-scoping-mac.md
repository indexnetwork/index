# Research: Intent scoping for the mac app

## Research Question
When a mac user chooses an intent as scope, all opportunities should come from that specific intent; all questions should be generated via that intent, opportunities from that intent, and negotiations for those opportunities.

## Summary
The mac prototype already passes the full intent object from the signal shelf into `pickExistingIntent`, but `App` collapses it to display-only profile fields and drops the stable `intent.id`. That id is the necessary join key for scoped API questions and the likely retrieval filter for opportunities generated by from-intent discovery. Direct intent-refinement questions are already supported by the backend as `mode=intent&sourceType=intent&sourceId=<intentId>`, while negotiation questions are keyed to opportunity ids, so the mac app must join selected-intent opportunities to `mode=negotiation&sourceType=opportunity` questions. Opportunity generation already persists the trigger intent in `detection.triggeredBy`, but REST list/home retrieval and pair-wide accept/start-chat side effects are not intent-scoped today. The main implementation risk is letting the UI filter locally while backend list/mutation semantics remain broader than the selected signal.

## Detailed Findings

### Mac selected-intent boundary
- `App` reads `PEOPLE`, `POOL`, `FIELD_EVENTS`, and `INTENTS` from `window.HALO_DATA`, then initializes `people` globally from every visible and hidden person (`apps/mac/HaloApp/src/halo-amiga/app.jsx:5-11`).
- `Intents` reads the global `INTENTS`, orders active/idle/paused rows, and passes each full `intent` object to the row callback (`apps/mac/HaloApp/src/halo-amiga/intents.jsx:4-11`, `apps/mac/HaloApp/src/halo-amiga/intents.jsx:103-110`).
- The stable id survives until the click boundary: `IntentRow` receives the full `intent` and `onPick` is already bound to `onPickExisting(intent)` (`apps/mac/HaloApp/src/halo-amiga/intents.jsx:126-135`).
- The id is lost in `pickExistingIntent`, which writes only `intent`, `edges`, `offLimits`, and `shape` into `profile` before switching to `main` (`apps/mac/HaloApp/src/halo-amiga/app.jsx:60-68`).
- `MainView` receives `profile` and the global `people` array, not a selected intent object or selected intent id (`apps/mac/HaloApp/src/halo-amiga/app.jsx:105-117`, `apps/mac/HaloApp/src/halo-amiga/mainview.jsx:30-32`).
- `MainView` then derives signal display/chat grouping from `profile.intent`, a title string, and derives all radar people from `people.filter(p => !p.hidden)` (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:166-172`).

### Mac saved-intent counts and API mapper seam
- Fake `INTENTS` include stable ids, `pipeline`, scalar `questions`, and `inbound` arrays (`apps/mac/HaloApp/src/halo-amiga/data.jsx:465-543`).
- The shelf UI displays only the scalar `intent.questions`; `inbound` is not used by the shelf rendering path (`apps/mac/HaloApp/src/halo-amiga/intents.jsx:129-179`).
- API mappers already treat API `intent.id` as the count key: `mapIntents` counts pending questions by `question.detection.sourceId` and passes the count into `mapIntent` (`apps/mac/api/mappers.mjs:51-80`, `apps/mac/api/mappers.mjs:226-231`).
- `mapIntent` preserves the raw API object as `source`, so a mac row can retain canonical API fields even while matching the current prototype shape (`apps/mac/api/mappers.mjs:61-80`).
- `mapHaloSnapshot` can compose a `HALO_DATA`-like payload with mapped `INTENTS`, `PEOPLE`, `POOL`, and `CLARIFIERS` from API inputs (`apps/mac/api/mappers.mjs:180-197`).
- The API boundary is intentionally standalone and not imported by HaloApp yet (`apps/mac/api/client.mjs:1-5`, `apps/mac/api/index.mjs:1-17`).

### Selected-intent opportunity retrieval
- The mac API client can already serialize arbitrary opportunity query params because `opportunities.list(query)` and `opportunities.home(query)` pass the object through `toQueryString` (`apps/mac/api/client.mjs:120-122`, `apps/mac/api/client.mjs:189-196`).
- `OpportunityController.listOpportunities` currently parses only `status`, `networkId`, `limit`, and `offset`, then calls `opportunityService.getOpportunitiesForUser` with those options (`services/api/src/controllers/opportunity.controller.ts:48-73`).
- `OpportunityService.getOpportunitiesForUser` accepts `status`, `statuses`, `networkId`, `limit`, and `offset`, and defaults unfiltered list calls to live statuses (`services/api/src/services/opportunity.service.ts:284-303`).
- `OpportunityDatabaseAdapter.getOpportunitiesForUser` filters visibility, draft visibility, status/statuses, network scope, and pagination, but has no `intentId` or `detection.triggeredBy` condition (`services/api/src/adapters/opportunity.database.adapter.ts:72-147`).
- `OpportunityController.getHome` and `OpportunityService.getHomeView` similarly accept network/limit/noCache/statuses but no intent filter (`services/api/src/controllers/opportunity.controller.ts:110-120`, `services/api/src/services/opportunity.service.ts:219-235`).
- Home feed generation deduplicates by counterpart user before the mac mapper sees cards, which can hide a second opportunity for the same person from another intent if intent filtering is not applied before home graph card generation (`packages/protocol/src/opportunity/feed/feed.graph.ts:199-231`).
- For selected-intent radar, scoping must occur before `MainView` receives `people`, because `MainView` currently trusts its `people` prop and only sorts/partitions it by status (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:166-172`).

### From-intent opportunity generation
- `FromIntentJobData` carries `intentId`, `userId`, and optional `networkIds` (`services/api/src/queues/opportunity/from-intent.queue.ts:13-17`).
- From-intent discovery loads the triggering intent, uses `intent.payload` as the search query, passes `triggerIntentId: intentId`, and sets `options.initialStatus` to `latent` (`services/api/src/queues/opportunity/from-intent.queue.ts:83-122`).
- The opportunity graph writes `detection.triggeredBy: state.resolvedTriggerIntentId` when discovery source is intent-based (`packages/protocol/src/opportunity/opportunity.graph.ts:2956-2962`).
- The same persist block stores actors, interpretation, context, confidence, status, and metadata on the opportunity row (`packages/protocol/src/opportunity/opportunity.graph.ts:2956-2981`).
- The generation side therefore preserves the trigger intent; the retrieval gap is that the mac-facing REST list/home paths cannot query that relationship today.

### Pending-question filtering
- `AdapterQuestionFilters` supports `mode`, `sourceType`, `sourceId`, `networkId`, `conversationId`, `noConversation`, `modes`, and `limit` (`services/api/src/adapters/questioner.adapter.ts:88-103`).
- `QuestionerAdapter.findPending` always filters to pending, actor-visible, non-expired questions, then applies exact JSONB detection filters for mode/sourceType/sourceId (`services/api/src/adapters/questioner.adapter.ts:145-184`).
- `QuestionController.list` exposes `status`, `mode`, `sourceType`, `sourceId`, `conversationId`, and `noConversation` as query params and calls `questionService.findPending` (`services/api/src/controllers/question.controller.ts:43-91`).
- The mac client `questions.pending(filters)` maps directly to `/questions?status=pending&...filters` (`apps/mac/api/client.mjs:142-145`).
- The mac mapper preserves `question.detection` as `sourceMeta` and the raw question as `apiQuestion`, so UI state can retain exact mode/source ids (`apps/mac/api/mappers.mjs:148-169`).

### Direct intent questions versus negotiation questions
- Questioner queue persistence copies `mode`, `sourceType`, and `sourceId` from the job into `detection` (`services/api/src/queues/questioner.queue.ts:153-161`).
- Intent backfill jobs use `mode: 'intent'`, `sourceType: 'intent'`, and `sourceId: row.intentId`, matching the exact filters exposed by the question API (`services/api/src/cli/backfill-intent-questions.ts:139-145`).
- Negotiation graph enqueues stalled/capped negotiation questions with `mode: 'negotiation'`, `sourceType: 'opportunity'`, and `sourceId: state.opportunityId` (`packages/protocol/src/negotiation/negotiation.graph.ts:415-421`).
- The answer dispatcher treats negotiation `sourceId` as an opportunity id and stores negotiation context against that opportunity (`services/api/src/events/handlers/question.answer.handler.ts:94-102`).
- Negotiation answers append to `opportunity.metadata.userAnswers` and do not directly move the opportunity into a ready/pending status (`services/api/src/events/handlers/question.answer.negotiation.ts:56-70`).
- Therefore “questions generated via the selected intent” has two categories: direct intent questions by selected intent id, plus negotiation questions whose source opportunity belongs to the selected intent.

### Local mac question feed
- Prototype clarifiers are global static data in `CLARIFIERS` and are attached to `window.HALO_DATA` (`apps/mac/HaloApp/src/halo-amiga/data.jsx:300-389`, `apps/mac/HaloApp/src/halo-amiga/data.jsx:543`).
- `MainView` reads `CLARIFIERS` directly and seeds the conversation feed with static items on mount (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:33`, `apps/mac/HaloApp/src/halo-amiga/mainview.jsx:75-106`).
- `makeClarifier` assigns random UI ids and copies fake clarifier fields into conversation items; no backend id is involved (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:83-101`).
- `answerClarifier` marks the local item answered, applies fake effects, and refills from static clarifiers; it never calls `/questions/:id/answer` (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:184-201`).
- `QuestionController.answer` expects `{ selectedOptions, freeText? }`, verifies the authenticated user is an actor, updates status, and emits the mode/source answer event (`services/api/src/controllers/question.controller.ts:102-136`, `services/api/src/adapters/questioner.adapter.ts:202-225`).
- API-backed selected-intent questions should replace static feed generation at the `makeClarifier`/seed boundary or be merged as primary rows deduped by backend `question.id`.

### Negotiation prompt display
- Static negotiation prompts are defined in `PERSON_QUESTIONS`, selected by hashing a person id/name, and recovered by prompt text (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:1338-1357`).
- `groupQuestions` groups negotiating people by derived prompt text, then `ConversationPane` renders those grouped prompt cards before the scrollback (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:974-980`, `apps/mac/HaloApp/src/halo-amiga/mainview.jsx:898-905`).
- `CollectiveQuestionCard` and `PersonQuestionCard` call `onRespond(p.id, answer)` with only person ids and text, not backend question ids or opportunity ids (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:1067-1096`).
- `respondPerson` locally changes the person status to `ready`, stores the answer, and appends an answered synthetic clarifier (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:258-282`).
- Backend-backed negotiation prompts need to carry both `question.id` and `question.detection.sourceId` (opportunity id), because the current person-id/prompt-text grouping is insufficient for answering real questions.

### Status mapping and scoped mutations
- `mapOpportunityStatusToPrototype` maps backend `pending`/`draft` to prototype `ready`, `negotiating`/`stalled` to `negotiating`, `accepted` to `accepted`, and `latent` to `considering` (`apps/mac/api/mappers.mjs:202-218`).
- `mapPeopleFromOpportunities` sets the mac person card id to `opportunity.id`, maps status, hides latent opportunities, and preserves the raw opportunity under `source` (`apps/mac/api/mappers.mjs:124-140`).
- `MatchCard` renders accept/pass/start-chat actions from `person.status`, while prototype handlers currently mutate local person state by id (`apps/mac/HaloApp/src/halo-amiga/mainview.jsx:1379-1472`, `apps/mac/HaloApp/src/halo-amiga/mainview.jsx:284-294`).
- The API client already exposes row-level `updateStatus(opportunityId, status)` and `startChat(opportunityId)` methods (`apps/mac/api/client.mjs:132-139`).
- `OpportunityController.updateStatus` and `startChat` resolve the supplied opportunity id for the user, but do not take selected intent as a guard (`services/api/src/controllers/opportunity.controller.ts:184-217`, `services/api/src/controllers/opportunity.controller.ts:233-258`).
- Accepting an opportunity triggers `acceptSiblingOpportunities` after the selected row update (`services/api/src/services/opportunity.service.ts:532-539`).
- `acceptSiblingOpportunities` accepts all non-terminal opportunities for the same actor pair except the selected row, without checking source intent, actor intent, or network (`services/api/src/adapters/opportunity.database.adapter.ts:319-348`).
- Developer clarified that in mac selected-intent scope, accepting Alex under Signal A should only accept that Signal A opportunity, not Alex under Signal B.

## Architecture Insights
- The stable selected intent id is the load-bearing state boundary. The shelf has it; App drops it; MainView needs it or pre-scoped data derived from it.
- Questions already have a mature scope/filter shape. The closest existing template is the `QuestionController.list` → `QuestionerAdapter.findPending` path, which exposes exact mode/source filters and enforces them SQL-side.
- Opportunity scoping is less complete than question scoping. Generation persists trigger intent, but retrieval, home-feed presentation, and sibling mutations do not yet expose or enforce selected intent scope.
- Negotiation questions cannot be fetched by `sourceId=<intentId>` because their source id is the opportunity id. The selected-intent feed needs an opportunity join before including negotiation questions.
- The mac mapper layer intentionally preserves raw `source`/`apiQuestion` data, which is useful for scoped row-level actions without forcing the UI to understand every backend field.
- Home feed deduplication by counterpart can conflict with intent scoping when the same counterpart has opportunities under multiple signals; selected-intent narrowing should happen before counterpart dedupe.
- Pair-wide acceptance is currently a backend domain side effect. For mac selected-intent flows, developer intent is row/signal-scoped acceptance.

### Composite Lessons
- Enforce selected-intent scoping at API/SQL boundaries, not only in mac UI state.
- Keep count and list semantics aligned; scoped signal badges and scoped radar should not be derived from different universes.
- Treat direct intent questions and negotiation questions as two joined datasets, because they use different `sourceId` meanings.
- Avoid pair-wide side effects in scoped mac actions unless they are explicitly product-approved for that surface.
- Keep mac API boundary changes in source modules and tests; generated bundles are a separate assembly step.
