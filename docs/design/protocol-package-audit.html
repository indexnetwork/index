01 · Executive verdict

Keep the boundary; recover the modules.

The package is valuable and cohesive at the product level. Its central architectural decision—host infrastructure injected through TypeScript ports—is sound. The problem is not that the package lacks domain names; it is that a broad shared layer, a single all-capability tool context, and a 306-symbol barrel make those domain folders permeable and costly to reason about.

Recommendation

Evolve toward a pragmatic domain-first modular monolith, with explicit public facades per capability and separate foreground/background runtime adapters. Do it incrementally behind the existing root export surface. Do not rewrite the graphs, ports, or package API in one pass.

Decision in four lines

  • Yes to domain-first modules.
  • No to a big-bang directory migration.
  • Preserve port injection and root exports.
  • Treat foreground/background as a second axis.

What is healthy

  • Zero imports from API/web implementation code.
  • Build passes under strict TypeScript.
  • Ports isolate persistence, queues, cache, transport, and embeddings.
  • Provider-free eval verification passes all nine suites.

What obscures the design

  • shared imports back into feature folders.
  • Tool composition knows every domain at once.
  • Foreground transport flags sit beside domain dependencies.
  • Large graphs combine orchestration, policy, persistence, and presentation.

What not to do

  • Do not remove exports based on local usage alone.
  • Do not replace ports with direct backend dependencies.
  • Do not make “internal” and “external” top-level domains.
  • Do not move 50,000 LOC before boundary tests exist.

Why the current layout is hard to understand

1 · “Shared” is not inward-only

Feature areas import shared code heavily, but shared code also has 38 static edges back into 11 feature areas. A reader cannot assume that shared is a stable lower layer.

2 · Composition is a dependency hub

tool.factory.ts imports tool creators for agent, contact, enrichment, integration, intent, negotiation, network, opportunity, premise, questioner, and utility capabilities.

3 · Ports are too aggregated

Database has 105 members; UserDatabase 42; SystemDatabase 34. ToolContext has 54 members. Injection exists, but the objects conceal capability boundaries.

4 · Public API mirrors internals

The root exports 306 symbols from 107 modules. Although deep imports are unsupported, the barrel exposes many helpers and state shapes, so internal moves carry compatibility review cost.

5 · Domain and runtime concerns coexist

MCP flags, personas, sessions, foreground tool behavior, async run stores, queues, and graph dependencies share the same contexts. Mode branching is visible inside capability orchestration.

6 · Names encode history

Signal/intent, community/network/index, and retained profile-facing labels are legitimate compatibility constraints, but without facades they make directory names a poor guide to current protocol vocabulary.

04 · Domain map & execution axis

Foreground and background are modes, not bounded contexts.

External/internal is a secondary interaction and runtime axis. A participant-triggered MCP call and an ambient queue job may both use the same signal, discovery, or negotiation application service. Conversely, one external agent call may cross several domains. Making external/ and internal/ the primary taxonomy would duplicate rules and hide the actual business boundary.

Interpretation

These scores describe branch count, not correctness. They are high because handlers combine admission, scoping, fallback, lifecycle, projection, error mapping, and asynchronous branching. The safe seam is to extract named application policies and pure decisions—not to turn every branch into a class.

  • Use Extract Function for pure policy decisions.
  • Use Guard Clauses for repeated admission checks.
  • Use Collapse Duplication for paired handlers only after variation is named.
  • Keep LangGraph node wiring close to the owning use case.

07 · Proposed target architecture

A domain-first modular monolith with runtime adapters around it.

Evidence supports a domain-first shape because opportunity, negotiation, signal, context, and community policies are substantial and change independently. The existing folders are the starting point. The target adds enforceable public/application/domain/infrastructure seams and moves interaction mode outside the primary domain tree.

Dependency rules

  1. domain imports only its own domain and small platform value types.
  2. application imports its domain, its ports, and other modules only through public.
  3. infrastructure implements protocol-owned graph/model bindings; it never implements host DB/cache/queue adapters.
  4. runtime composes module facades and selects foreground/background behavior.
  5. platform imports no module internals.
  6. index.ts preserves every supported export name while paths move underneath.

About “infrastructure”: inside this published package it means technology-specific protocol mechanics such as LangGraph builders, LangChain model bindings, and MCP codecs. Host persistence, Redis, BullMQ, Drizzle, and delivery implementations remain outside and arrive through ports.

How the public and injection boundaries survive

Compatibility facade

Keep src/index.ts as the only supported package entry. Re-export moved symbols under the same names and stability tiers. Additions may be minor; removals follow the documented deprecation/major path.

Capability ports

Slice the 105-member Database into module-owned reader/writer ports. Preserve the existing composites as compatibility intersections so host adapters continue to satisfy them structurally.

Composition stays outside

Runtime factories accept the same host implementations. Domains call injected interfaces; they never import services/api, schemas, queues, or concrete adapters.
