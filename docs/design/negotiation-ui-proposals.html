Negotiations — where they live & how they look

Candidate placements and presentation patterns for agent-to-agent negotiations in the web app. Every mockup below uses the product's real tokens (IBM Plex Mono / Public Sans, navy #041729, steel #4091BB, sharp radii, emerald/amber/red status) and its real domain vocabulary, so each option can be judged as it would actually feel.

§0

The object we're designing for

A negotiation is not a priced bargain and not a human chat. It is a bilateral agent-to-agent dialogue game that quality-gates a proposed match: two agents debate one fixed proposition — "this connection serves both clients" — over a handful of turns, and produce a verdict plus role assignments. Anything we show users must respect four facts.

1 · It's a transcript, not a terms document

Each turn carries an action (propose / counter / question / accept / decline / withdraw), reasoning, and suggested roles. The artifact is the dialogue itself.

2 · Three status layers, never one

Dialogue state (in progress / waiting / concluded) ≠ opportunity status (negotiating → pending / rejected / stalled) ≠ human action (accept / pass). Conflating them is the main UX failure mode.

3 · Agent accept ≠ human accept

When agents agree, the opportunity becomes pending — "agents recommend this". Only a human "Start chat" writes accepted. The human gate must always be visible.

4 · It's asymmetric and partially invisible

Only the counterparty seat can accept; the initiator can only walk away. A screened_out negotiation must render as never happened to the other side. Users can be consulted mid-game via ask_user.

negotiating ──agents agree──▶ pending ──human: Start chat──▶ accepted (H2H DM opens) negotiating ──decline / withdraw──▶ rejected ──turn cap──▶ stalled (can be revived via follow-up question)

Roles use user-facing vocabulary: Helper / Seeker / Peer (internal: agent / patient / peer). Existing surfaces today: NegotiationHistory on profiles, the Messages/Negotiations toggle in the chat sidebar, a read-only transcript page, the negotiator DM with ask_user cards, and Telegram "your move" digests. The question this document answers: what should the system of surfaces be?

§1

Where negotiations should surface — three placements

Negotiations are event-driven, multi-threaded agent work with three distinct user postures: act (your move), watch (agents are working), and review (resolved). The placement question is really: which surface owns triage? Here are the three credible answers.

A A first-class "Negotiations" inbox new TopBar item · dedicated route, e.g. /negotiations

Promote negotiations from the chat-sidebar toggle to their own top-level destination: an inbox grouped by posture — Your move, In progress, Resolved. This mirrors the buckets the Telegram digest already computes (needsAttention / waiting / newlyResolved) and gives "my agent is working for me" a visible home.

Key detail — lifecycle labels, not raw statuses. Rows never say working or input_required; they say what it means for the user: "Answer your agent", "Live · turn 3 of 6", "Agents agreed · awaiting your accept". This is the narration contract the API already ships for MCP clients.

Why it works

  • One canonical place to answer "what are my agents doing?" — trust through visibility.
  • Owns triage: the "Your move" queue is unambiguous and countable (TopBar pill).
  • Negotiations stop impersonating conversations — no longer buried under Chat.
  • Same buckets as the Telegram digest → coherent cross-surface mental model.

Costs / risks

  • Fifth TopBar destination — only justified if negotiation volume is real, otherwise an empty room.
  • Duplication with the chat-sidebar toggle must be resolved (keep toggle as convenience, or redirect it here).
  • Needs the inbox data (grouping + "your move" flag) — mostly present in GET /conversations/negotiations + lifecycle labels, some assembly required.

§2

How a negotiation should look — the component kit

Four components cover every state of the lifecycle. All obey one rule: a negotiation never wears the visual skin of a human DM (no bubbles, no left/right chat alignment) — it is rendered as agent work: verbs, reasoning, and verdicts.

2.1 · The live card — in-flight visibility inbox "In progress" · opportunity card · signal radar

While agents are talking, show just enough to build trust without demanding attention: who's talking, how far in, the latest move in one line, and an explicit promise that nothing is final.

Y your agent ⇄ AK Aisha's agent Live
turn 3 of 6
COUNTERED their agent · 12m ago

"Time commitment is the open point — proposing async-first collaboration with a monthly sync instead of weekly calls."

Watch live Agents negotiate — you decide. Nothing is agreed until you accept.

Deliberately not a progress bar toward "success": the turn cap is a budget, not a completion meter. The amber pulse is the only animation — negotiations are background work and should feel calm.

2.2 · The consultation card — ask_user (your move) inbox "Your move" · negotiator DM · Agent questions

When a negotiator pauses to consult its own client, that is the single most important moment in the whole lifecycle — the human's only in-game lever. It deserves the strongest visual priority in the system, and a privacy promise rendered as part of the card, since the answer is disclosed to no one but the user's own agent.

Your move Your agent is asking · about Mira Chen 23h left

"Their agent asked how much time you could realistically give a collaboration. What should I say?"

Your agent paused the negotiation to check with you. This is the only question it will ask in this negotiation.

A few hours a month, async only… Send
🔒 Only your agent sees this. It decides what, if anything, to disclose.

If the 24h window lapses, the card decays to a quiet "window missed — negotiation continued without an answer" line in the transcript; it must never look like an error the user caused.

2.3 · The transcript — concluded or watched negotiations detail view (from inbox row, sidebar row, or card)

The reading view. A vertical rail (the existing NegotiationHistory idiom), upgraded with seat labels, role-suggestion chips, and an outcome banner that separates what agents agreed from what you do about it.

Verb colors follow the product's existing action palette (proposed = blue, countered = amber, questioned = steel, accepted = emerald, declined/withdrawn = red). Reasoning is shown verbatim — transparency is the trust mechanism — while ask_user answers and anything screened_out never appear.

2.4 · The resolved states — rejected & stalled inbox "Resolved" · profile history

Negative outcomes are where tone matters most. The agents did their job by filtering; the UI should frame that as protection, not failure — and stalled negotiations should offer a path back rather than a corpse.

No opportunity — filtered out for you

After 6 turns, the agents couldn't justify this connection: Jonas needs a full-time collaborator, which doesn't match your stated availability. You were never notified while this played out.

Jonas's side never learns the details — declines are quiet by design.

Stalled — agents ran out of turns

The dialogue hit its 6-turn budget without agreement; open question: commitment level. Sometimes a stalled thread is one answer away from resolving.

Answer the open question Let it go

Answering routes through your agent and can revive the negotiation.

Note the honesty rule on the left card: don't claim the other side "rejected you" when your own agent screened it — and never reveal a screened_out to the counterparty at all. Phrasing follows outcome.reason (screened_out / turn_cap / timeout) with hedged language, as the presenter spec prescribes.

§3

Recommended system

Combine the placements by job-to-be-done rather than picking one winner: an inbox to triage, contextual cards to decide, the negotiator DM to deliberate.

Design principles carried through all of the above
  • Never impersonate chatNegotiations are rendered as agent work — verbs, reasoning, verdicts — never as human DM bubbles. The two threads (A2A transcript vs. H2H chat) stay visually unmistakable.
  • Verdict first, transcript on demandProgressive disclosure: outcome + your role up top; the full dialogue one tap away for trust, not on the critical path.
  • The human gate is always visibleWherever an agreement is shown, so is the fact that only the human's "Start chat" makes it real. Agent accept never auto-commits anything.
  • One "your move" queueThe same triage buckets drive the web inbox, TopBar pill, and Telegram digest, so "what do I owe my agent?" has one answer everywhere.
  • Calm by default, loud onceLive negotiations pulse quietly in the background; the only loud state in the system is a consultation card waiting on you.
  • Honest negativesRejections and stalls are framed as filtering done for you, with hedged reason-based phrasing — and screened-out threads are invisible to the other side, always.

Smallest honest first step: ship 2.1's templated live chip on opportunity cards and the grouped inbox (Option A) fed by the existing negotiations list — both are presentation-layer changes over data the API already serves. The consultation card's inbox presence can follow since ask_user already flows through the questions pipeline.
